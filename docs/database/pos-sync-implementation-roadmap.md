# POS sync implementation roadmap

Use one durable upload queue and one authorized cloud download feed. A committed business action wakes the uploader immediately. A private Supabase Realtime signal wakes connected clients to fetch committed cloud changes. The normal flow runs throughout the business day. Durable positions let a terminal catch up after a disconnect or missed signal. Source revisions remain internal and protect concurrent edits and repairs. A software release version has a separate role in client and server compatibility.

## Installed database and current paths

- The local `POS_Local` database runs SQL Server 2025 Express, build `17.0.1145.4`, EngineEdition `4`. Change Tracking is on with seven-day retention and automatic cleanup. CDC, snapshot isolation and read-committed snapshot are off. Express includes Change Tracking. No package is required. Keep the durable queue as the source of pending work, retain Change Tracking where a verified legacy writer needs it, and defer a native CDC adapter unless a supported deployment has a concrete need for one. [Microsoft SQL Server 2025 edition matrix](https://learn.microsoft.com/en-us/sql/sql-server/editions-and-components-of-sql-server-2025?view=sql-server-ver17#replication)
- Windows connects to SQL Server through the existing Microsoft ODBC Driver 18 and `mssql/msnodesqlv8`. Both Change Tracking and a future CDC adapter use that same connection. Windows already journals some financial aggregates in the SQL transaction and scans pending journal work directly. Its download worker applies dependency-ordered rows and a cursor in one SQL Server transaction. Windows sync reaches the hosted relay over HTTPS. Web and Android use that relay and the browser outbox. Preserve their normal entry points as the cloud protocol evolves. [ODBC connection](../../electron/db/connection-manager.cjs) · [Windows sync](../../electron/sync) · [Browser outbox](../../src/lib/browser-sync-outbox.ts)
- The connected POS Supabase project has the durable row feed, batch receipts and the Realtime publication for `authorization_requests`. All 70 registry tables exist on both sides. The installed SQL Server catalog has 94 user tables and zero user views. Supabase `public` has 80 tables and three views, and other schemas include managed, private and preparation relations. [SQL Server inventory](pos-sync-sqlserver-inventory.readonly.sql) · [Postgres inventory](pos-sync-postgres-inventory.readonly.sql) · [Current registry coverage](../audit/sync-table-coverage-20261105.md)

The 24 SQL Server tables outside the row registry are local journal, checkpoint and conflict state, operational jobs and counters, schema history, operation receipts, and 17 shift author and financial support tables. Their business effects travel through the existing protected protocol. Of the 10 unmapped public Postgres tables, nine are explicitly server-only. They cover session state, SKU allocation, notification deliveries, sponsorship policy and issues, missed-bill provenance, the feed and idempotency receipts. The remaining public table is schema migration history. Private, managed and preparation schemas still require explicit relation-level disposition in the rollout registry. ## Implementation and verification gaps

1. **Approval delivery.** A screen opened before staff verification now joins scoped Realtime as soon as verification completes and refreshes after joining. Holds subscribes to the same store it reads. Add an authenticated, minimal wake for relay-only PIN users and a recipient-scoped wake for named cross-store approvers. Include new, approved, rejected, expired and claimed requests, held-ticket readiness and notification badges in acceptance. A wake triggers the authorized queue read. A claim still validates the person, request, ticket contents and one-time use. Make decision, audit and wake publication recover together if one part fails. [Approval client](../../src/lib/approval-centre.ts) · [Approval server](../../src/lib/authorization.functions.ts)
2. **Complete table and writer inventory.** Match SQL Server and Postgres tables, views, partitions, keys, dependencies and mapped fields. Record an explicit disposition for cloud-only, local-only, internal and restricted relations. For each synced projection record direction, ownership, allowed fields and writers, scope, conflict and deletion policy, recovery, retention and acceptance. Trace every checkout, tender, refund, void, cash, stock, shift, settings, admin and import writer. Fail the rollout gate if an installed application relation or writer lacks a disposition.
3. **One upload queue with durable business evidence.** Reuse the current journal where its durability and replay contract suffice. Convert critical row pointers to immutable, typed operation payloads committed with the business write. Preserve stable operation and business IDs, the original payload, dependencies, the originating installation and retry state. Keep the local commit wake, direct queue scan, reconnect and bounded retry on the same sender. For retained legacy Change Tracking reads, validate the range and consistent read boundary before advancing. The current database has snapshot isolation off, so rehearse any required setting change on an isolated copy. [Current journal](../../electron/db/shift-sync-journal.cjs) · [Current capture reader](../../electron/sync/change-reader.cjs)
4. **Transactional acceptance and recovery.** Apply each cloud operation, its durable disposition and its feed group together. Return the recorded result for the same operation and payload. Keep conflicting payloads and missing dependencies recoverable without reposting ledger effects. Add status lookup for interrupted uploads and restores. Verify provider idempotency and uncertain payment recovery separately from POS delivery, using the actual supported payment methods and offline rules.
5. **Commit-ordered cloud feed.** The current identity cursor is assigned to individual rows before commit. A later transaction can expose a higher cursor while an earlier transaction is still open. A page limit can also split one transaction. Introduce an ordered stream of complete change groups per authorized scope, with a committed upper bound, replay floor, epoch and lossless cursor serialization. Acquire scope heads in deterministic order when a write spans scopes. Emit removals for the old scope when records move. Preserve the existing scoped history and mixed-client rollout safeguards. [Feed generator](../../scripts/generate-supabase-sync-contract.cjs) · [PostgreSQL sequence semantics](https://www.postgresql.org/docs/current/functions-sequence.html)
6. **Independent upload and download progress.** Ordinary failures already allow some work in the other direction. An expired local capture range can block the existing shared pass because downloads must protect pending edits and shift graphs. Split progress by independently authorized scope, preserving those local write guards. Keep the affected cursor at the last complete group when application fails. Keep device revocation fail-closed and confirm a downloaded change creates no echo upload. [Coordinator](../../electron/sync/coordinator.cjs) · [Download worker](../../electron/sync/pull-worker.cjs)
7. **Snapshot and expired history recovery.** Build a scoped, checksummed snapshot at a pinned feed position, stage it and catch it up before activation. Activate the cache and its cursor together. Preserve pending sales, tenders, open shifts and the local journal throughout. Resume uploads from the original operation IDs and protect acknowledged financial history with retained evidence or backup. A feed epoch change uses the same controlled rebuild.
8. **Date and time repair with verified convergence.** Allow bounded UTC windows only for projections with source-owned change times, revisions and deletion coverage. Keep repair progress separate from normal delivery. Verify both sides at a common committed boundary using mapped values and keys or deterministic hashes. Use financial operation and ledger IDs as well as totals. Record unresolved differences and route ambiguous financial evidence through review. Existing count checks and separately timed signatures cannot establish this boundary. [Reconciliation](../../electron/sync/reconciliation.cjs) · [Verifier](../../electron/sync/verifier.cjs)
9. **Shift and shared drawer rules.** Confirm the real drawer ownership, offline operations, business-day cutoff, and maximum expected outage for each pilot. Preserve the existing author proofs, closure fences and verified recovery. Cover gaps before closure, late activity, authorized forced closure and tills that share a drawer. Persist the original business date, amounts and tender evidence across reconnect, midnight and clock changes.
10. **Operator health and restore.** Report last upload and download, oldest pending operation, capture and feed lag, required review and snapshot progress. Expose specific failure reasons while preserving credentials and payload privacy. Confirm retention, backup and restore targets and fence stale enrolled copies before replay. The seven-day CT window must not set the lifetime of unacknowledged business operations.
11. **Staging, cutover and handback.** Validate against an isolated SQL Server Express database and an isolated Supabase environment with production-equivalent schema and permissions. Establish a common baseline and stable ID mapping. Rehearse one real checkout and shift lifecycle through offline commit, reconnect, interrupted replay, cursor expiry and rollback. Include a pending sale and open shift. Compare IDs and effects on both sides. Fence the old sender before enabling the replacement and retain its pending evidence. Test one pilot scope before expansion or retirement of compatibility paths.

The connected Supabase project provides a read-only baseline. It is production-connected and does not serve as the isolated acceptance environment. The local approval tests cover late verification, subscription teardown and the fallback path. Installed two-terminal delivery and the replacement protocol remain pending.
