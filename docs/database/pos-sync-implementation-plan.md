# POS Sync Implementation Plan

The full POS sync replacement is pending. Implement **two-way synchronization between SQL Server 2025 Express and Supabase Postgres**. The POS uploads sales and other business actions from one durable local journal. SQL Server **Change Tracking (CT)** detects changes on selected legacy tables where the latest row state is sufficient. The POS downloads approved cloud changes from a durable Supabase feed. Realtime wakes connected clients to fetch changes immediately, and checkpoints resume delivery after missed signals or outages.

For each authorized sync scope, SQL Server and Supabase must converge on the same synced records and business field values after they process the same committed changes. Verify that match after recovery and during routine reconciliation. Pending operations and device-specific fields have separate local state.

```text
SQL Server POS  -- upload events and authorized changes -->  Supabase Postgres
SQL Server POS  <-- download canonical data and results --  Supabase Postgres
```

### When each method runs

| Method | When it runs | What it does |
|---|---|---|
| **Business events** | As part of a POS business action such as completing a sale, opening a shift, or recording a refund, online or offline. | Commit the business data and a named event such as `SaleCompleted` to SQL Server together. A local wake-up can start uploading immediately when connected. The outbox keeps the event available for later delivery. |
| **SQL Server Change Tracking** | In the background for approved legacy tables where the latest committed state is sufficient. | Discover changed keys and deletions from a CT checkpoint. The uploader sends approved current-state changes. If the checkpoint expires, rebuild those mirrors while the business journal continues sending pending operations. |
| **Supabase feed and Broadcast** | When Supabase commits an admin change or applies a POS upload. | Append a durable download entry. Broadcast wakes connected registers. Registers also pull on a timer and after reconnect using their last applied sequence. |
| **Date-and-time repair** | When a known incident window or reconciliation check identifies missing or mismatched data. | Find candidate records in an overlapping time window. Repair eligible copies using the owning source's committed version, and reconcile business events by operation and business IDs. |
| **Snapshot or journal recovery** | When usable history has expired, the scope has drifted, or the time-window result cannot establish completeness. | Rebuild current-state copies from a verified snapshot and resume at its checkpoint. Replay missing financial operations from the durable journal or recover the journal from backup. |

A cashier can finish an approved offline cash sale and keep working. SQL Server commits the receipt and its event together. When connectivity returns, the uploader reads the pending event. Supabase applies it once, adds a download entry, and eligible registers pull the confirmation. A cloud price change starts at the Supabase feed and travels in the download direction.

## 1. Start with the existing application

Use this as the implementation brief. A read-only query verified `POS_Local` on `.\LCRPOS` runs SQL Server 2025 Express, build `17.0.1145.4`, with CT enabled. Reuse the existing Windows ODBC Driver 18 connection and the HTTPS sync relay. Inspect the application repository, migrations, and both schemas to map the design to the current code. The Express cutover uses CT and the durable journal. Treat a native CDC adapter as a separate decision for a future CDC-capable deployment. [SQL Server 2025 edition matrix](https://learn.microsoft.com/en-us/sql/sql-server/editions-and-components-of-sql-server-2025?view=sql-server-ver17#replication)

### Four requirements before cutover

1. **Approvals appear promptly.** Keep the staff subscription after verification. Give PIN-only tills an authenticated wake and send named cross-store approvers only their own authorized signals. Update the open screen and the in-app badge while the signed-in app is running. See section 5 for background behavior and timing.
2. **Every critical action leaves a durable record.** Prove that each sale, refund, void, tender, cash movement, stock movement, and shift transition commits its replayable event with the business change. Reuse one uploader. A retry must return the same result and produce one payment and stock effect.
3. **Downloads arrive whole and in order.** Replace the cloud row cursor with commit-ordered change groups. A missed signal triggers catch-up from a saved position. An expired position triggers a staged snapshot that keeps pending sales and open shifts.
4. **Both databases agree before the switch.** Classify all application tables and writers, assign ownership for editable fields, and verify the same synced values after recovery. Run the cutover and handback drill on two isolated tills before replacing the live sync engine.

### Discovery and decisions for the pilot

1. Trace checkout, tenders, refunds, voids, stock movement, cash movements, shift open and close, and all cloud admin/import paths. Locate the current sync worker, retry state, ID mappings, date filters, and the actual code or log entries for history expiration and shift expiration. Check whether multiple tills share a SQL Server instance or a cash drawer.
2. Start with the 70 registered tables reported to exist on both sides. Inventory the remaining relations in both schemas and classify them explicitly. Include local support, cloud-only, managed, private, and staging relations, along with dependencies and permitted writers. Compare the completed registry with the installed schemas before the rollout.
3. Confirm the operating rules in section 7 with the store. Record the actual drawer ownership, store time zone and business-day cutoff, offline actions and limits, and cross-store approval rights. Use the proposed defaults to build and test the pilot.

### Table types and sync rules

Use the table's purpose and permitted writers to choose its policy. The examples below describe categories Codex should map to the real schema. Tables in the same business operation share its transaction boundary. If a physical table mixes authorities, define ownership and allowed fields explicitly for each projection or operation.

| Table type and examples | Direction and normal sync | Date-and-time role and gap recovery |
|---|---|---|
| **POS transactions** such as sales, lines, tenders, returns, voids, discounts used on receipts, and cash movements | Upload complete business events directly from the local outbox. Download canonical results and any authorized cross-register history. Apply related rows and ledger effects once per operation. | Use business date, receipt time, or shift to find records. Reconcile by operation, sale, and tender IDs. Replay the original journal or recover it from backup. |
| **Shifts and drawer sessions** such as opening floats, activity, counts, and close records | Upload lifecycle events and journal entries from the owner. Download confirmed status, authorized supervisor decisions, and related store-shift state. | Use business date and opening time to locate sessions. Reconcile by shift ID and activity sequence, including sessions that span multiple dates. |
| **Inventory and shared financial balances** such as stock movements, gift cards, loyalty, and store credit | Upload authorized movement or balance commands. Download authoritative availability, balances, and status. Resolve contention centrally, with explicit offline allowances if the business supports them. | Find affected movements by time, then replay or reconcile by movement ID. Rebuild balances from their authoritative projection or ledger. |
| **Cloud-owned reference and configuration** such as catalog, categories, tax, price lists, promotions, and store settings | Download the scoped durable feed, including deactivations. Retain rule versions needed by checkout. | An approved timestamp scan can repair current rows and tombstones. Use a scoped snapshot if completeness cannot be verified. |
| **POS-owned reference and configuration** such as store-specific data maintained locally and needed in the cloud | Upload through an explicit event or an allowlisted CT mirror. Where every direct SQL edit is required, use a targeted transactional journal. Apply the same source identity, scope, and version checks at ingestion. | The owning SQL Server can supply a timestamp repair for current rows if the requirements in section 6 are met. Otherwise compare or rebuild from its scoped baseline. |
| **Shared editable records** such as eligible customer details, customer notes, or product metadata that both sides can edit | Upload typed commands with an expected version. Cloud edits use the same validation. Download canonical revisions. Define field ownership and conflict policy per operation. | Scan canonical current state for eligible cache repair. Resolve pending local edits by command ID and version, even when timestamps differ. |
| **Dependent rows and relationship tables** such as barcode mappings, product assignments, and order children | Follow the parent or aggregate's policy and scope. Group changes with the parent when consistency requires it. | Repair the full affected aggregate or partition. Include removals and moved relationships. |
| **Append-only audit and integration logs** required centrally | Upload or download the authorized stream from the producer. Deduplicate by immutable entry ID and use the producer's durable cursor or journal. | Use time ranges to locate retained entries. Check coverage by stable IDs or producer sequence before marking the window complete. |
| **Attachments and media metadata** such as product photos or receipt files | Sync scoped metadata and content references through the parent route. Transfer file contents separately with resumable downloads or uploads and checksums. | Identify affected objects by time, then verify by object ID, version, and checksum. Reconcile deletions through metadata. |
| **Identity and access** such as staff assignments, permissions, and revocations | Download an allowlisted, scoped authorization projection if offline operation needs it. Use authorized account workflows for mutations and a dedicated re-enrollment path for device recovery. | Revalidate with the authority and refresh the projection when integrity or freshness is uncertain. Keep credentials in the identity system. |
| **Derived and transient data** such as reports, caches, search indexes, and import staging | Recompute from authoritative data or download a designated projection. Staging tables have no independent replication route. | Rebuild the affected partition or projection from a verified boundary. |
| **Local-only, cloud-only, restricted, and sync-internal tables** such as print spool, device UI state, billing admin, credentials, outbox, inbox, and checkpoints | Keep data in its owning system. Transfer approved business events and protocol responses through their dedicated routes. Record the reason each table is excluded from row replication. | Use the owning system's recovery procedure. Preserve device and capture checkpoints separately from cloud feed checkpoints. |

### Required sync registry fields

For every table, record `local_table`, `cloud_table`, `table_type`, `direction` (`upload`, `download`, `both`, or `excluded`), permitted writers, authorized scope and fields, primary or composite key mapping, aggregate and dependencies, normal upload and download modes, timestamp eligibility and source column, source version, delete or tombstone behavior, conflict rule, bootstrap and recovery route, retention, and acceptance test. Record an exclusion reason where relevant. A table with direction `both` needs an explicit rule for each write direction and conflict scenario.

## 2. Persistence and identifiers

Reuse current domain tables and transactions where possible. The names below describe responsibilities and can map to existing repository conventions.

| Location | Record | Minimum contract |
|---|---|---|
| SQL Server | `pos_outbox` | Stable `operation_id`, originating installation, tenant/store/register, aggregate and shift IDs, dependency IDs, event type and schema version, immutable payload, state, attempt count, and next retry time. Index sendable rows and keep the original payload available for recovery. |
| SQL Server | `pos_sync_state` | Local source generation, durable CT version per tracked table or atomic group, cloud feed epoch and last applied sequence per scope, snapshot progress, and last successful contact. Keep CT and download checkpoints separate from pending journal state. |
| Supabase Postgres | `sync_inbox` | Unique `(tenant_id, operation_id)`, originating device, canonical payload hash, durable disposition, and result or review reference. Keep deduplication evidence for as long as a historical operation can be retried. |
| Supabase Postgres | `sync_feed_head` and `sync_feed` | Head and replay floor per authorized scope and epoch. One feed record per atomic change group with `seq`, operation ID when applicable, payload version, and ordered upserts or removals. Index `(scope_id, epoch, seq)`. |
| Supabase Postgres | Domain ledgers and review cases | Stable business IDs, immutable facts, unique movement and provider references where applicable, and audited resolutions. Store enough context to reconcile a printed receipt or tender independently of the sync feed. |

Generate cross-database IDs before the first local commit, preferably UUIDs. Preserve legacy integer keys through an explicit mapping scoped to their origin. Reuse the same operation ID on every delivery attempt, and use separate stable IDs for sales, tenders, refunds, and stock movements. If a restored or cloned POS starts a new installation generation, preserve original IDs for all existing queued records and prevent the old and replacement instances from acting as the same register concurrently. Use explicit precision and currency for money, quantity, tax, and rounding. Serialize 64-bit counters without precision loss in JSON clients.

Run the upload and download loops independently and show their health separately. For example, register A can upload a sale, Supabase can confirm it, and register B can download its authorized projection. Both registers apply the downloaded state through the inbound path. That path records the source and revision and suppresses outbound capture of its own writes. Use CT only for registered, locally owned projections with a clear boundary between inbound and outbound writes. Keep the existing guards for unsent edits and shifts. Test that an inbound update produces zero echo uploads. Pending edits use explicit operations, so a download can refresh canonical state while preserving the unsent edit for validation or review.

## 3. Upload business events

Reuse the current financial journal and one Windows uploader where their transaction and replay guarantees suffice. Replace critical journal entries that only point to mutable rows with immutable typed payloads. Wake the uploader after a local commit, at startup, on reconnect, and on a periodic timer. Use a single worker lease per local queue or atomic row claims with reclaimable leases. Use exponential backoff with jitter for transport errors, timeouts, rate limits, and transient server failures. Keep each unacknowledged event independent of CT retention. Preserve the existing relay entry points for Windows, web, and Android during the protocol migration.

1. **Commit at the register.** In one fully durable SQL Server transaction, write the business change and its outbox record. For `SaleCompleted`, carry the sale and line IDs, quantities, original prices and tax, discounts, tender records or references, shift context, and the data required to post stock and accounting effects. Print or report checkout completion only after the local commit. Reprinting an existing receipt must reuse its sale ID. [SQL Server transaction durability](https://learn.microsoft.com/en-us/sql/relational-databases/logs/control-transaction-durability?view=sql-server-ver17), [Transactional outbox](https://learn.microsoft.com/en-us/power-platform/architecture/reference-architectures/transactional-outbox-pattern)
2. **Send the operation.** Expose a bounded `POST /sync/push` on the existing trusted backend or a Supabase Edge Function. Use per-operation results for a batch. A shift must precede its sales, and an original sale must precede a return against it. A blocked aggregate can wait while unrelated operations continue. Use stable dependencies and versions to enforce ordering on the server as well as the client.
3. **Apply in one Postgres transaction.** Verify the authenticated device's tenant, store, and register mapping and validate the operation. Claim the unique inbox key and serialize concurrent attempts. Commit the domain mutations, inbox result, and POS feed entry together. If an identical operation already committed, return its stored outcome. If the same ID arrives with different content, surface an integrity conflict. Add uniqueness to each domain effect so legacy overlap or a different operation ID cannot post the same sale, tender, or inventory movement twice. An Edge Function should call a single transactional database handler per operation or use a real Postgres transaction. Separate REST inserts cannot provide this boundary.
4. **Persist the disposition locally.** Acknowledge only after the server has durably recorded the outcome. Use `APPLIED` or `ALREADY_APPLIED` for confirmed results, `WAITING_DEPENDENCY` for retryable ordering, and `REVIEW_REQUIRED` for business conflicts that need resolution. Return canonical IDs and the resulting feed position where applicable. Persist review cases and retain the local evidence. Retry an unknown outcome with the same ID and payload. A correction is a new, linked operation. A status endpoint accepting batches of operation IDs lets the POS resolve interrupted uploads and restore cases.

Keep network calls outside database transactions. For card capture, refunds, and other external side effects, persist the intent and stable merchant reference before calling the provider. Use the same provider idempotency key where supported. If the result is uncertain, reconcile through a provider lookup or webhook before attempting another charge. This includes a crash between provider success and the local sale commit. Treat payment authorization, settlement, and POS sync as separate states. Offline card acceptance must follow the actual provider's supported offline mode and configured limits. Cash sales can follow the local commit path. The device must surface any declined or unconfirmed offline payment for reconciliation.

## 4. SQL Server Change Tracking and history recovery

CT survives a restart and tracks changed keys and operations within its retention window. The roadmap reports seven-day retention and snapshot isolation currently off. Confirm those settings on the pilot database. CT is for selected legacy mirrors. The uploader scans the business journal directly so a CT failure cannot strand an offline sale or expire a shift. [Microsoft's Change Tracking overview and retention](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/enable-and-disable-change-tracking-sql-server)

1. **Allowlist current-state mirrors.** Register the stable key, scope, writer, required columns, dependency group, and how to remove a deleted or moved record. Preserve the old scope through the key, a stored mapping, or a tombstone where required. Require explicit business events for financial operations and shared editable fields.
2. **Read a consistent CT window.** Rehearse enabling `ALLOW_SNAPSHOT_ISOLATION` on the isolated Express database. In a short SQL Server `SNAPSHOT` transaction, validate the previous version against `CHANGE_TRACKING_MIN_VALID_VERSION` for every table in the group, record the fixed upper `CHANGE_TRACKING_CURRENT_VERSION`, and read `CHANGETABLE(CHANGES ...)` and the source rows. Include delete markers. Durably stage all eligible changes before advancing the CT checkpoint, preferably in the same local transaction. Use the originating installation and source generation, table, key, scope, and change version to identify retries. Send to the relay after the transaction commits. [Microsoft's Change Tracking synchronization procedure](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/work-with-change-tracking-sql-server)
3. **Recover an expired or invalid version.** Put only the affected mirror in recovery. Materialize a consistent snapshot of the authoritative local scope with its CT version, stage it for verified application on the cloud, then catch up from that version. Rebuild again if retention overtakes the baseline before catch-up completes. Reconcile removals against the authorized mirror and verify matching data. On restore or CT reinitialization, assign a new source generation and rebuild. Keep the original pending events, financial evidence, open shifts, and independent cloud download cursors.
4. **Cover direct SQL writers.** Route critical business changes through the application or a shared transactional writer that creates complete business events. For an approved legacy table that needs every before-and-after change, use a set-based SQL trigger to write an allowlisted payload into the durable journal in the same transaction. Handle bulk edits and deletes and test for sync echoes. Keep CT for latest-state mirrors and choose one upload route per change. Cloud admin and import paths must publish to the cloud feed in their own transaction. [Microsoft's DML trigger documentation](https://learn.microsoft.com/en-us/sql/relational-databases/triggers/dml-triggers?view=sql-server-ver17)

## 5. Download changes from Supabase

Start with one logical feed per tenant and store for data that tills in that store are authorized to share. Use separate scopes for register-private data when required. Resolve shared catalog changes to their affected store scopes. Give every independently authorized scope its own cursor, and put changes that must apply together in the same scope and atomic group. Benchmark fan-out using actual store and catalog sizes before expanding the pilot.

Version the replacement feed and start it with a fresh epoch. The roadmap describes an existing row cursor that can skip an earlier transaction if a later row becomes visible first. Bootstrap pilot clients from a verified snapshot of the new feed and its position. Keep the old contract available for clients still on it during the rollout. If both feeds are published during transition, publish both in the same cloud transaction and keep one active upload route per till.

1. **Publish in commit order.** In the same Postgres transaction as a cloud mutation or an accepted POS operation, lock the scope's head row, advance its sequence, append the feed group, and update the state served by the snapshot. If a transaction touches several scopes, acquire scope locks in deterministic order. Use the committed head as the high watermark. A standalone identity or sequence assigned by concurrent writers can expose a later ID before an earlier transaction commits. [PostgreSQL sequence behavior](https://www.postgresql.org/docs/current/functions-sequence.html)
2. **Wake the POS.** Use a private Supabase Realtime Broadcast message containing only a scope notification after a feed change commits. On any notification, reconnect, startup, or periodic poll, fetch the durable feed from the last applied cursor. A missed message or disconnected WebSocket leaves the same changes available over the sync API. [Supabase Broadcast](https://supabase.com/docs/guides/realtime/subscribing-to-database-changes), [Realtime authorization](https://supabase.com/docs/guides/realtime/authorization)
3. **Pull a stable window.** `GET /sync/pull` takes a scope-bound cursor and page limit. The first response fixes a committed upper bound. Subsequent pages use `last_seq < seq <= upper_bound` and order by `seq`. Validate the replay floor and fetch the page from a consistent database view to avoid cleanup racing the read. Return whole groups, the next cursor, and whether more groups remain. On an expired cursor or epoch mismatch return a structured `SNAPSHOT_REQUIRED` result. Authorization failure and incompatible client schema have their own results.
4. **Apply locally.** In one SQL Server transaction, apply each complete group with parent rows before dependent inserts and safe deletion ordering, and persist the new cursor. Use stable entity IDs and versions to make replay safe. Apply soft deletes or explicit removal records, including a removal from the old scope when a record moves between scopes. Keep downloaded state separate from local transactions or mark its origin so it never creates an outbound business operation. An accepted local operation may remain visible as pending confirmation until the canonical effect is observed. Merge by operation and business IDs to show each sale once.

### Snapshot and resync procedure

Use the same procedure for first enrollment, an expired cloud feed cursor, a scoped cache repair, and a feed epoch change. Expose snapshot creation, a status/manifest endpoint, and authenticated chunk downloads.

1. Pin a feed position under the same coordination used by feed cleanup before generating the snapshot, so cleanup preserves the necessary deltas. From a single consistent Postgres snapshot, read the scoped state and its committed feed head `H`. Export immutable chunks with a manifest containing scope, epoch, `H`, schema version, row counts, and checksums. Include current reference data, applicable open sessions, and the historical context required by the terminal's permitted workflows. Use one consistent read across the export, such as a Postgres `REPEATABLE READ` transaction. [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html)
2. Download and verify the chunks into SQL Server staging. Apply changes after `H` through a fixed catch-up boundary. Pause normal pull application for the rebuilding scope so staging cannot replace a newer installed cursor. Keep the POS serving the prior cache where its offline policy permits. If a pin, download, or epoch becomes invalid, restart staging against a valid snapshot.
3. In one local transaction, activate the validated cache and its cursor together. Keep local sales, tenders, outbox, and active drawer sessions in durable local storage outside the replaced cache. Reconcile pending and accepted operations against canonical IDs or status before applying the local overlay to avoid duplicate sales. Serialize the activation with local writers so operations recorded during the rebuild survive it. Resume normal pull from the activated cursor and continue any outstanding uploads.

### Approval signals for staff and PIN-only tills

Require **both** a refresh of the open approval screen and an update to the in-app badge or notification area when another screen is open and the app is running with an active authorized session. Handle app-closed system notifications as a separate delivery requirement if store operations need them. Use a proposed pilot target of **95% of connected approval updates visible within two seconds** of commit on a healthy network. Retain the reported five-second authorized poll while the approval screen is visible as fallback. Refresh at sign-in, after staff verification, on reconnect or resume, and through a bounded background refresh while the authorized session is active.

1. **Staff sessions.** Start the existing scoped subscription as soon as verification finishes, even if the screen was already open, and refresh after joining. Align each holds or approvals subscription with the scope it reads.
2. **PIN-only tills.** Use the existing authenticated relay session to deliver a minimal wake for that till's authorized queue. A Realtime implementation requires a short-lived, scoped subscription credential issued by a trusted backend. The wake prompts an authorized relay read and carries no approval details or PIN. Poll the authorized relay when the signal is missed.
3. **Named cross-store approvers.** Authorize cross-store approval only when the request explicitly names the recipient and store policy grants that approval type. Send a recipient-scoped wake to the verified person. Recheck permission when fetching and claiming the request. Avoid exposing an entire other store's queue to the recipient.
4. **Commit the outcome before notifying.** Commit the request or decision, audit record, and durable notification work together. Send the wake after commit and allow it to be retried. Validate the acting person, current request state and expiry, ticket contents, and one-time claim in the relay. Re-read after new, approved, rejected, expired, or claimed status changes. Update held-ticket readiness and the badge from the authorized response. [Supabase Realtime authorization](https://supabase.com/docs/guides/realtime/authorization)

## 6. Date and time based recovery

Use a time range to identify affected changes when sync has stalled or data is missing. Resume business uploads by operation ID, legacy mirrors by CT version, and cloud downloads by feed sequence. A time-range repair has its own progress and leaves those checkpoints intact. It can run for **upload** from a POS-owned source or **download** from Supabase for a cloud-owned source. The registry defines which data qualifies.

### Choose the recovery method

| What failed | Recovery method |
|---|---|
| Upload stopped, but the SQL Server outbox is intact | Scan sendable outbox records across all dates and resend the original operation IDs. Recover CT mirrors separately. Use the incident time to investigate the failure. |
| A SQL Server legacy mirror is behind or has an expired CT checkpoint | Use the last valid CT version for catch-up, or rebuild from an authoritative local snapshot with a new boundary if the version expired. Use timestamps for an eligible targeted repair, with verified coverage. |
| Downloads stopped, but the cloud feed cursor is valid | Replay from the last applied sequence. Use Realtime or the poller to resume fetching the feed. |
| A current-state catalog, configuration, or other eligible mirror is stale or has a known gap | Scan an overlapping time window at its authoritative source, repair through the allowed direction, and verify the resulting scoped state. If the cursor itself expired, use the snapshot or baseline procedure to establish a safe new cursor. |
| A sale, payment, shift, cash, or inventory movement is missing | Use date/time, business date, or shift ID to find candidates. Compare operation and ledger IDs, including entries posted after the reported incident. Replay original operations or recover the journal and reconcile unresolved evidence. |
| The affected time range, clock history, delete coverage, or authority is uncertain | Rebuild current-state data from a consistent scoped snapshot. Reconcile financial history from the durable journal or backup. |

### Resolve differences between SQL Server and Supabase

Start by comparing the same stable key, authorized scope, and mapped fields. Check pending uploads, the download cursor, and the source revision before diagnosing corruption. If a terminal is behind, let the valid stream catch up first and compare at an equivalent committed boundary. A time window can narrow the investigation even when the normal cursor is still valid.

| What differs | How to choose the value or action |
|---|---|
| A cloud-owned product, price, tax rule, or setting | Use the latest committed revision from Supabase for the affected store. For example, if Supabase has price revision 12 and the POS holds revision 11, download revision 12 even if the POS copy has a later local `updated_at` from an import. Apply price effective dates separately at checkout. |
| A POS-owned current-state record mirrored to Supabase | Use the owning register's committed revision and upload through its authorized route. Compare source revisions within the same source generation. A restore or ownership change calls for a verified baseline. |
| Both sides edited a shared field | Compare the local command's expected revision with the central revision. Merge only where the registered field rules permit it. For competing changes to the same field, use the configured conflict rule or send the case to review with both values and their audit times. |
| A sale, payment, stock movement, or shift entry differs or is absent | Match operation and business IDs, then check the committed journal and cloud inbox or ledger. Replay a missing original operation. A conflicting payload for an existing ID goes to review with both records preserved. Apply a reversal or adjustment when the business approves a correction. |
| The same source revision has different content | Verify mapped fields against the source at the same boundary. Restore an established cache copy from that authoritative state. Escalate ambiguous ownership or conflicting ledger evidence for review. |

Use UTC timestamps from the designated source to find changes and establish when they were recorded. Select current data using the source's committed revision and ownership rule. The databases' independent clocks and version counters can disagree, so a later timestamp alone cannot establish which copy is correct.

### Verify that both databases match after repair

1. **Apply the resolved value.** Repair the stale or missing copy through its authorized upload or download route. If resolving a conflict creates a new canonical value, commit the resolution and publish its revision for each authorized register to pull. Apply removals using an authoritative tombstone or verified snapshot. For financial records, use the original operation or an audited adjustment.
2. **Check a common boundary.** Compare consistent views of the same tenant, store, and table or aggregate after both sides reach the agreed source revision or feed position. Compare stable keys in both directions, source revisions where applicable, and all mapped business values. Normalize field formats per the registry, including decimal precision, null handling, and UTC timestamp precision. Deterministic partition hashes can narrow large comparisons to affected keys. Compare confirmed financial operations by ID as well as totals.
3. **Protect concurrent writes.** Recheck the source generation and destination revision before applying a repair. Apply eligible repairs conditionally so a newer revision committed during the scan wins. When the boundary changes during comparison, use the pinned views or repeat verification at a newer common position. Keep local pending edits as separate operations until their outcomes are known.
4. **Record the outcome.** Save the scope, compared positions, mismatched or missing keys, and repair result. A scope is reconciled only after matching synced values and expected removals are verified. Keep unresolved differences visible as `catching_up` or `review_required`, as appropriate. Alert when the discrepancy exceeds the agreed recovery time and rerun verification after resolution.

### Implement a bounded timestamp scan for eligible tables

1. **Prove eligibility.** Allow only explicitly registered current-state projections or mirrors with a stable key, authorized scope, and a source-managed UTC `sync_changed_at` maintained on every relevant insert and update. Verify normal app writes, admin edits, imports, and migrations. Preserve versioned tombstones or soft deletes for deletions and scope moves. Use the source's revision and epoch for precedence. An existing `updated_at` qualifies only if it meets these requirements. SQL Server's `timestamp` type is an alias for `rowversion` and stores a version number. [SQL Server rowversion](https://learn.microsoft.com/en-us/sql/t-sql/data-types/rowversion-transact-sql)
2. **Fix the scope and window.** Record direction, table or aggregate, source epoch, tenant/store, and the reason for the repair. Convert an operator's date and time from the selected store's time zone to UTC. For automatic repair, start at the last verified healthy boundary or earliest suspected change, minus a configurable overlap. Set a fixed exclusive end using source database time and a safety lag sized for observed commit and replication delays. Record the window even when zero rows are returned. PostgreSQL `CURRENT_TIMESTAMP` reflects transaction start, and a change timestamp can precede commit. Overlap and lag reduce omissions, while scoped verification is required for completeness. [PostgreSQL time functions](https://www.postgresql.org/docs/current/functions-datetime.html), [SQL Server change tracking and commit order](https://learn.microsoft.com/sql/relational-databases/track-changes/track-data-changes-sql-server)
3. **Page consistently.** Read from a consistent snapshot or materialize a stable candidate list before paging. Include rows and tombstones where `start_utc <= sync_changed_at < end_utc`. Use keyset pagination on `(sync_changed_at, primary_key)`, with all components of a composite key when applicable. Store the repair page cursor only after its changes or candidates are durable. Index scope, timestamp, and key for eligible tables. Restart if the source epoch changes.
4. **Apply with existing write rules.** On upload, submit versioned data for the POS-owned scope through the normal authenticated ingestion path. On download, apply the Supabase projection with the same version, scope, deletion, and dependency checks used for the feed. Deduplicate overlapping pages. Use explicit tombstones for removal and check that the incoming revision is current. A row absent from a time window may simply have changed earlier. Preserve local pending operations and suppress sync echoes.
5. **Verify and resume.** Compare scoped keys and revisions, with deterministic content hashes where required, against the authoritative state at an equivalent committed boundary. Re-scan the overlap for late arrivals. Keep the incident open if coverage cannot be established or tombstones are missing. Use a scoped snapshot or authoritative baseline with catch-up in that case. Resume the normal stream using its valid cursor or the snapshot's new cursor.

For example, after a catalog download failure, scan products and deactivations from Supabase over the affected UTC window and verify the store's catalog. If a sale from that same window arrives from the register two days later, upload it by its original operation ID and keep the business date assigned at checkout. Its later arrival does not depend on the window scan.

### Business dates and clocks

- Record the device-reported occurrence time in UTC, its observed offset, the configured store time-zone identifier, cloud receipt time, and the assigned `business_date`. Use SQL Server `datetimeoffset` or an explicit UTC `datetime2` convention and Postgres `timestamptz`. Persist the original offset and zone separately where needed. Preserve raw device time for troubleshooting and surface clock drift to operators.
- Compute `business_date` using the store's approved cutoff and shift attribution rule. For example, a shift assigned to November 7 can keep that business date when a sale occurs after midnight if the store assigns sales to the shift's opening business date. Persist the rule version used. Test midnight, changed time zones, and daylight-saving transitions where applicable. Cloud arrival time should never reassign an offline receipt to a later business day.
- Record the effective price/tax version used at checkout and the actual receipt amounts. Apply the approved stale-catalog policy for creating new sales. Route already recorded transactions with invalid or stale rule evidence to reconciliation under the approved policy.
- Use UTC for retry and health records and monotonic elapsed timers where available. Run synchronization after connectivity returns and on a jittered polling interval. Scheduled overnight jobs may reconcile totals or clean retention windows. Delivery must continue throughout the business day.

## 7. Offline operation and drawer policy

### Proposed operating rules for the pilot

Exercise **24 hours of offline operation** as the initial pilot target and simulate a CT retention expiry separately. Confirm a production offline limit per store and enforce it for new actions using approved offline permissions and cached rules. Retain and upload already committed operations at any age. Escalate when the offline limit, cached policy validity, or local storage headroom is exceeded.

| Action | Pilot rule during an outage |
|---|---|
| **Cash sale** | Allow on an authorized till with a valid drawer session, approved cached price and tax rules, and a successful durable local commit. Record the receipt amounts, tender, shift, and sale-related stock movements together. |
| **Card payment** | Allow only after the actual provider's certified offline workflow, limits, and status recovery have been verified for this deployment. Otherwise require online card processing. Preserve the original provider reference and surface later declines or uncertain outcomes for reconciliation. |
| **Refund or void** | Require online validation for refunds and reversals of completed sales or tenders in the pilot. Allow an authorized cashier to cancel an unpaid draft on the originating till. |
| **Cash movement** | Allow a movement on the till's own drawer only when the cached permissions explicitly allow it. Record the actor, reason, amount, and drawer sequence. Require an online approval when policy calls for one. |
| **Stock movement** | Record sale-related movements atomically with an approved offline sale. Require online validation for standalone adjustments and transfers in the pilot. Configure the store's offline stock allowance or oversell policy before enabling offline sales. |
| **Shift open or close** | Allow an authorized till to open and record a local close for its own drawer. The cloud confirms close after it has all required activity and reconciles totals. For a shared drawer, use one designated owner or require online coordination to finalize the count. |
| **Approvals, shared balances, and high-risk actions** | Require an online authorized decision for actions that need a supervisor or shared balance check. Keep pending requests visible and revalidate before claim. |

Confirm one independently owned drawer per till as the pilot assumption. Record the store's actual time zone, business-day cutoff, and sale-to-shift attribution rule in configuration before live use. Reuse the store's approved reporting rule. Use a test cutoff such as 04:00 in staging to exercise sales on both sides of midnight and the cutoff. Preserve the assigned business date and original receipt amounts when uploading later.

### Shift state and closure

Model `OPEN → CLOSE_PENDING → CLOSED` with an explicit review disposition for conflicts. Persist the session ID, register/drawer ownership, cashier, business date, opening float, times, cash movements, and close count. Keep the drawer state independent of sign-in, heartbeat, midnight, CT cleanup, and terminal restart. A long-open shift raises an operational alert. A new cashier login or refreshed credential can resume the authorized session and sync queued activity.

1. **Open offline.** Generate the shift and drawer session IDs on the owning register. Commit `ShiftOpened` and the opening float locally. Enforce one active local session per physical drawer. At the cloud, serialize opening against the drawer and enforce the corresponding uniqueness rule. If two devices opened the same drawer while partitioned, preserve both journals and flag the ownership conflict.
2. **Record activity offline.** Assign a per-session sequence in the same local transaction as each journal entry that affects closure, including sales, refunds, and cash movements. Maintain contiguous sequence coverage, with one unique ID per entry. Bind a sale to its explicit shift and drawer session IDs. Use dependencies to make the cloud wait for the opening record if necessary.
3. **Close offline.** Commit the counted cash, expected totals, variance, and last activity sequence in `ShiftClosed` locally. Fence new entries on that session when the cashier closes it. Cloud close stays pending until all required entries through the declared final sequence are accounted for and the totals reconcile, including any required review or tender status. The register can open its next session under the approved policy, with a dependency on its predecessor's close or a supervised handoff as appropriate.
4. **Handle late activity and forced closure.** Accept a valid delayed entry up to the declared close sequence while the close is pending. A supervisor force-close records the actor, reason, and known cutoff and marks unresolved activity for review. A late entry after finalization, a competing session, or a discrepancy creates an auditable exception. Preserve the original receipt, tender, and cash evidence. Resolve via an approved adjustment or accounting workflow.
5. **Support shared shifts explicitly.** If multiple registers work under one store shift, use a parent shift with independently owned drawer sessions and finalize the parent after all participant sessions have checked in or been handled by a supervisor. If multiple terminals truly share one cash drawer while disconnected, require an online coordination point or one designated drawer owner. A single terminal cannot verify a complete shared cash count during a partition.

## 8. Failure handling and retention

| Scenario | Required result |
|---|---|
| Internet or Supabase outage | Continue approved local operations. Retain pending records and show last sync, pending count, and oldest pending age. Automatically resume uploads and pulls after reconnect. |
| One direction fails while the other is healthy | Keep the healthy direction running within its dependencies. Show upload and download statuses separately. Recover the failed route from its checkpoint, using the scoped date/time repair or snapshot procedure when applicable. |
| Server commits and response is lost | Resend the same ID. Return the stored outcome and produce one financial effect. |
| POS or worker crashes during a pull | Either the group and its cursor committed together, or replay the group from the earlier cursor. |
| Worker is stuck, a CT read fails, or Realtime is unavailable | Supervise and restart a stuck worker and reclaim its leases. When CT or Broadcast fails, continue using the direct outbox scan and feed pull where safe. Alert on the failed component and preserve its last valid checkpoint. |
| Dependency is absent or the operation cannot be applied | Park the dependent operation with a reason. Let unrelated operations proceed. Preserve original data and give supervisors a status and resolution path. |
| Local clock is reset or credentials expire | Keep committed data and shift assignments. Renew access on reconnect. Enforce offline authorization limits for new actions separately from uploading captured evidence. |
| Snapshot is interrupted or fails validation | Retain the previous cache and local records. Retry the staged download or request a new snapshot. |
| A malformed operation or feed group repeatedly fails | Preserve the payload and reason. Isolate the upload and its dependent operations while unrelated work continues. For a failed download group, retain the scope's cursor before that group and recover with a compatible client, corrected replay, or a verified snapshot. |
| A restored POS starts while the original is still running | Use the enrollment generation to fence the stale installation from cloud writes and protect drawer ownership. Preserve pending operations from both copies for authorized reconciliation by original ID. |
| A terminal moves stores or loses permission for a scope | Stop serving the old scope, retire its cursors and subscriptions, and enroll the new scope with a fresh authorized snapshot. Preserve any pending old-scope transactions in a protected recovery workflow. |
| Many registers reconnect together or the API rate-limits them | Back off with jitter and honor server retry guidance. Bound batch size and concurrency. Preserve order within dependencies and preserve whole atomic groups when adapting batch size. |
| Terminal disk is full, damaged, or lost | Alert before capacity exhaustion. Stop acknowledging new sales if the durable local commit fails. Recover from a tested local backup or secondary durable copy. An unsynced transaction on a lost device is recoverable only if a separate durable copy exists. |
| Supabase is restored to an earlier point | Rotate the feed epoch before reopening sync. Restore canonical facts and deduplication receipts, reconcile provider references and retained terminal journals, and replay missing operations with their original IDs. Use new snapshots for the repaired epoch. |

Choose retention separately for each layer. Size **CT history** for the maximum expected legacy-mirror worker outage plus recovery margin. Size the **cloud feed** for the desired time that an offline register can resume without a snapshot. Size by measured peak bytes and change rate, and alert on remaining headroom. Keep all unresolved local operations regardless of age. Archive confirmed local evidence and cloud deduplication records according to the period during which retry, audit, restore, or reconciliation remains possible. A feed snapshot replaces the downloadable cache, while historical receipts and financial journals follow the application's records policy.

Set recovery point and recovery time targets for both databases. Keep an encrypted local recovery copy as required by those targets. Validate the Supabase backup and Point-in-Time Recovery setup on the actual project. If the business requires recovery of acknowledged cloud operations even after the database is restored to a point before those operations, keep recoverable copies outside the rollback boundary and define when acknowledgment is allowed. A snapshot alone cannot recover missing financial facts. [Supabase backups and Point-in-Time Recovery](https://supabase.com/docs/guides/platform/backups)

## 9. Security and operations

- Keep inbox, feed, snapshot metadata, and internal handlers in a private Postgres schema where practical. Use an enrolled device identity and an authenticated operator or device session as appropriate. Derive tenant, store, and register access from server-side assignments. Recheck revocation on the sync API. Use least-privilege grants and RLS for exposed tables, including Realtime topic authorization. Use a backend-only database connection or credential. Keep Supabase service-role and secret keys off the POS. Authorize snapshot chunks by device and scope, including any retry or download URLs. [Supabase data security](https://supabase.com/docs/guides/database/secure-data)
- Use a scoped SQL Server account for the worker. Limit capture columns and download payloads. Redact personal information and payment references from diagnostic logs as appropriate. Keep privileged payload inspection in an audited support workflow.
- Expose per-terminal health for upload backlog age, last successful upload and pull, CT and feed lag, reseeds, storage headroom, incompatible versions, approval wake and fallback, and open or pending-close shifts. Alert on differences in sales, tender, cash, and inventory totals. Include operation IDs and failure reason codes in diagnostics. Distinguish `offline`, `catching_up`, `snapshot_rebuild`, and `review_required` in the operator and support views.
- Reconcile at an agreed checkpoint. Compare operation receipts and financial totals by store, drawer session, business date, tender, and currency. For current-state data, compare scoped counts and deterministic hashes at the same feed watermark. Diagnose missing IDs individually. Repair reference caches through snapshots and resolve financial discrepancies through the business workflow.
- When data is missing, trace a known operation through the local commit and outbox, cloud inbox, canonical row and feed entry, and the terminal's applied cursor. Check the device's scope and the registered writer before declaring a feed healthy. Use controlled staging transactions to test the full route and detect paths that update data without publishing.

## 10. Implementation and rollout sequence

Use two Windows tills or equivalent staging instances with separate device enrollments and independent SQL Server 2025 Express databases. Suggested database names are `POS_Sync_Staging_A` and `POS_Sync_Staging_B`. The production-connected Supabase project can serve as a read-only baseline.

Use **Central database URL**, **API key (publishable)**, and **POS backend / website address**. The sync worker uses those saved settings and the existing local SQL Server profile.
